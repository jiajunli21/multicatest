# 用户积分系统 — 阶段计划文档

> 产出阶段：BEW-2（后端 Leader / 需求拆解与计划）
> 生成时间：2026-05-14
> 上游输入：BEW-1（积分系统全流程自动化编排）

## 1. 需求目标

构建一个用户积分系统，为平台用户提供积分全生命周期管理能力，支撑营销激励、用户留存等业务场景。

核心目标：

- 支持积分获取，可通过多种渠道（活动、任务、管理员发放等）为用户增加积分
- 支持积分消费，用户可使用积分兑换权益或抵扣
- 支持积分冻结与解冻，用于风控审核、交易争议等场景
- 提供积分明细查询，用户可以追溯每一笔积分变动

## 2. 功能范围

### 2.1 积分获取

- 用户通过指定渠道获取积分（渠道类型可扩展：活动奖励、任务完成、签到、管理员手动发放等）
- 积分获取时支持设置过期时间
- 积分获取需记录来源渠道、关联业务单号

### 2.2 积分消费

- 用户消费积分用于兑换或抵扣
- 优先消费即将过期的积分（FIFO/按过期时间优先扣减）
- 消费时校验余额充足性，余额不足则拒绝
- 消费需记录关联业务单号（如订单号）

### 2.3 积分冻结与解冻

- 支持冻结指定用户的指定数量积分（如风控需要）
- 冻结期间积分不可消费，但仍在用户账户中
- 支持解冻操作，恢复积分可用状态
- 支持扣减已冻结积分（如确认违规后扣除）
- 冻结需记录原因和操作人

### 2.4 积分明细查询

- 按用户 ID 分页查询积分变动明细
- 支持按变动类型筛选（获取、消费、冻结、解冻、扣减）
- 支持按时间范围筛选
- 明细包含：变动金额、变动类型、变动后余额、关联业务单号、时间戳

### 2.5 积分余额查询

- 查询用户当前可用积分余额
- 查询用户冻结积分余额
- 查询用户总积分（可用 + 冻结）

## 3. 非目标

以下内容明确不在本次范围内：

- **积分兑换规则引擎**：积分的具体兑换比例、商品定价规则由业务层定义，本系统只负责积分账务
- **前端 UI**：本阶段仅做后端 API，不包含页面实现
- **积分过期定时任务**：过期策略的定时执行由外部调度系统负责，本系统需提供"查询即将过期积分"的能力，但不内置定时器
- **积分等级/会员体系**：基于积分累计值的等级和权益体系不在范围
- **积分转让/赠送**：用户之间的积分转移不做
- **多币种积分**：当前只有一种积分类型
- **实时通知**：积分变动后的消息推送不在本系统范围，但需提供事件钩子供外部系统消费

## 4. 核心业务流程

### 4.1 积分获取流程

```
客户端请求 → 校验参数（用户、渠道、金额、业务单号）→ 写入积分明细（类型=获取）
→ 更新账户可用余额 → 返回最新余额
```

关键约束：
- 幂等性：同一业务单号不允许重复获取
- 金额必须 > 0
- 支持可选过期时间

### 4.2 积分消费流程

```
客户端请求 → 校验参数 → 查询账户余额 → 校验可用余额 >= 消费金额
→ 按过期时间升序扣减积分明细（优先消费即将过期的积分）→ 写入消费明细
→ 更新账户可用余额 → 返回最新余额
```

关键约束：
- 余额不足时拒绝，返回明确错误码
- 消费需关联业务单号保证幂等
- 冻结积分不计入可用余额

### 4.3 积分冻结流程

```
客户端请求 → 校验参数 → 查询可用余额 → 校验可用余额 >= 冻结金额
→ 扣减可用余额 → 增加冻结余额 → 写入冻结明细 → 返回结果
```

### 4.4 积分解冻流程

```
客户端请求 → 校验参数 → 查询冻结记录 → 校验冻结余额充足
→ 扣减冻结余额 → 增加可用余额 → 写入解冻明细 → 返回结果
```

### 4.5 冻结积分扣减流程

```
客户端请求 → 校验参数 → 查询冻结记录 → 校验冻结余额充足
→ 扣减冻结余额（不调整可用余额）→ 写入扣减明细 → 返回结果
```

## 5. 领域对象

### 5.1 PointAccount（积分账户）

| 字段 | 类型 | 说明 |
|------|------|------|
| id | string (UUID) | 主键 |
| user_id | string | 用户 ID，唯一 |
| available_balance | int64 | 可用积分余额 |
| frozen_balance | int64 | 冻结积分余额 |
| total_earned | int64 | 累计获取积分（不可变递增） |
| total_spent | int64 | 累计消费积分（不可变递增） |
| version | int32 | 乐观锁版本号 |
| created_at | timestamp | 创建时间 |
| updated_at | timestamp | 更新时间 |

### 5.2 PointTransaction（积分明细）

| 字段 | 类型 | 说明 |
|------|------|------|
| id | string (UUID) | 主键 |
| user_id | string | 用户 ID |
| type | enum | 变动类型：EARN / SPEND / FREEZE / UNFREEZE / DEDUCT |
| amount | int64 | 变动金额（正数） |
| balance_after | int64 | 变动后可用余额 |
| frozen_after | int64 | 变动后冻结余额 |
| source | string | 来源渠道标识 |
| reference_id | string | 关联业务单号（幂等键） |
| expires_at | timestamp | 过期时间（仅 EARN 类型有效，可选） |
| metadata | json | 扩展信息 |
| created_at | timestamp | 创建时间 |

### 5.3 FreezeRecord（冻结记录）

| 字段 | 类型 | 说明 |
|------|------|------|
| id | string (UUID) | 主键 |
| user_id | string | 用户 ID |
| amount | int64 | 冻结金额 |
| remaining | int64 | 剩余冻结金额（解冻/扣减后递减） |
| reason | string | 冻结原因 |
| operator_id | string | 操作人 ID |
| status | enum | 冻结状态：ACTIVE / RELEASED / DEDUCTED |
| metadata | json | 扩展信息 |
| created_at | timestamp | 创建时间 |
| updated_at | timestamp | 更新时间 |

## 7. 测试关注点

### 7.1 单元测试重点

- 积分余额加减计算逻辑的精度验证
- 消费时 FIFO/按过期时间优先扣减逻辑
- 幂等性校验（重复业务单号）
- 边界值：金额为 0、负数、超大数据
- 乐观锁冲突重试

### 7.2 集成测试重点

- 并发消费场景下余额一致性（多个请求同时消费）
- 冻结期间消费被正确拒绝
- 解冻后积分可正常消费
- 跨类型明细查询的正确性和分页准确性

### 7.3 异常场景

- 用户不存在时的处理
- 余额不足时的错误响应
- 重复业务单号时的幂等响应
- 数据库连接失败时的降级行为

## 8. 风险与边界情况

### 8.1 技术风险

| 风险 | 影响 | 缓解措施 |
|------|------|----------|
| 并发扣减导致余额超扣 | 资金损失 | 乐观锁 + 数据库行锁，余额不足时回滚 |
| 幂等键冲突导致重复请求被误判 | 用户体验差 | 幂等键设计为 (user_id + type + reference_id) 联合唯一 |
| 积分过期时间边界 | 积分过期判断不准 | 统一使用服务端时间，明确过期时间精度为秒级 |
| 冻结积分后忘记解冻 | 用户投诉 | 冻结记录独立存储，支持按冻结记录查询和批量管理 |

### 8.2 业务边界

- 积分金额使用 **int64** 存储，最小单位为"分"，避免浮点精度问题
- 单次积分操作金额上限建议设置为可配置项，默认值给一个合理上限（如 1,000,000 分/次）
- 用户积分账户在首次积分获取时自动创建（lazy creation），避免预创建海量空账户
- 冻结操作需要记录操作人，便于审计追溯

### 8.3 扩展性预留（本期不实现）

- 积分类型字段预留枚举扩展位（当前仅 SINGLE），便于后续支持多积分类型
- 明细表 metadata 字段为 JSON，业务方可自行扩展自定义信息
- 积分变动事件可输出到消息队列（预留事件结构定义），供通知/审计等下游消费
